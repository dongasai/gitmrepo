# git mrepo fix

交互式检测并修复模块仓库的异常状态。

## 用途

扫描 `.gitmrepo` 中已注册的模块，找出目录缺失、缺少 `.git`、`.git` 损坏等问题，并提供**克隆修复**与**关联修复**两种策略恢复 Git 管理。

**核心场景**：

- `sync` 之后某几个模块没拉下来（目录不存在）
- 手工拷贝/解压过代码目录，导致模块只有文件没有 `.git`
- `.git` 目录被误删或内部结构损坏，`status`/`pull`/`push` 全部失败

## 使用方法

```bash
git mrepo fix [module] [--batch]
```

## 参数

| 参数 | 类型 | 说明 | 默认值 |
|------|------|------|--------|
| `[module]` | 可选 | 模块名称或路径，指定后只修复该模块 | 交互式多选 |
| `--batch` | 可选 | 批量模式，只自动修复**警告级别**问题 | false |

## 可修复的问题

| 问题类型 | 严重级别 | 检测条件 | 可选修复方式 |
|----------|----------|----------|--------------|
| `missing_directory` | critical | 模块目录不存在 | 克隆 |
| `missing_git` | warning | 目录存在但没有 `.git` | 重新克隆 / 关联修复 |
| `git_corrupted` | critical | `.git` 缺少 `HEAD`/`config`，或 `git rev-parse` 失败 | 重新克隆 / 关联修复 |

## 修复策略对比

| 优先级 | 策略 | 适用类型 | 现有文件 | 说明 |
|------|------|----------|----------|------|
| 1（默认） | 关联修复 `attach` | `missing_git` / `git_corrupted` | ✅ 完整保留 | 克隆到临时目录后搬移 `.git`，把现有文件恢复到 Git 管理下 |
| 2 | 重新克隆 `clone_force` | `missing_git` / `git_corrupted` | ⚠️ **会被删除** | 清空目录后重新克隆，内容以远程仓库为准 |
| - | 克隆 `clone` | `missing_directory` | 无（目录不存在） | 直接从远程 `git clone -b <branch>`，该类型仅此一个选项 |

> 判断依据：本地有未提交/未推送的修改时用**关联修复**；确定本地内容与远程一致或已无用修改时用**重新克隆**。

## 使用示例

```bash
# 交互式：列出所有有问题的模块，空格多选
git mrepo fix

# 只修复单个模块
git mrepo fix auth-service
git mrepo fix modules/auth

# 批量：自动修复所有 warning 级别问题
git mrepo fix --batch
```

## 执行流程

```
┌─────────────────────┐
│ 读取 .gitmrepo 配置  │
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│ detectModuleIssues  │ 逐个模块体检
│ 目录存在? .git 健康? │
└──────────┬──────────┘
           ↓
     有问题吗? ── 否 → 提示"状态正常，无需修复" → 结束
           ↓ 是
   ┌───────┴────────┐
   │                │
指定 module?     --batch?
   │                │
   ↓                ↓
单模块修复      分类：critical / warning
   │                │
   │        有 critical → 打印清单 + 提示改用交互模式
   │        仅 warning → 逐个 attach 修复并输出报告
   ↓
列出修复选项 → 用户选择 → 执行修复 → 验证 .git 健康 → 更新配置
```

## 实现要点

- **问题检测**：`detectModuleIssues()` 依次检查目录存在性、`.git` 存在性、`.git` 完整性（`HEAD`/`config` + `git rev-parse --git-dir`）
- **关联修复**：复用 `attachDirToRemote()`——远程克隆到临时目录，把 `.git` 搬回模块目录，现有工作区文件保持不变
- **分支校正**：关联修复后若实际分支与配置不一致，会自动回写 `.gitmrepo` 中的 `branch` 字段
- **严重级别的作用**：critical 问题（目录不存在 / `.git` 损坏）涉及不可逆的数据操作，`--batch` 不会自动处理，必须交互确认

## 注意事项

- 修复选项列表默认选中第一项（关联修复），直接回车即采用保留内容的方案
- 运行前先把重要改动提交或备份，尤其是选择**重新克隆**会 `rm -rf` 整个模块目录
- `missing_directory`（目录不存在）只有克隆一种选项，若远程不可达则修复必然失败
- `--batch` 只处理 `warning` 级别；存在 `critical` 问题时它会停止并建议你改用交互式
- 修复单个模块时也可以传路径，会先按模块名匹配再按路径匹配（走 `findModule`）
- 关联修复要求本地目录结构大致匹配远程仓库，否则修复完成后 `git status` 会显示大量差异，需要人工处理
- 修复失败会打印原因并继续下一个模块，不会中断整个流程

## 与其他命令对比

| 命令 | 作用 | 是否会改动文件 |
|------|------|----------------|
| `status` | 查看模块状态并使用同样的体检逻辑标记异常 | 否 |
| `sync` | 按配置 clone / pull 全部模块 | 可能 |
| `add` | 把已是 Git 仓库的目录登记进配置 | 否 |
| `attach` | 把无 `.git` 的目录关联到远程 | 否（新增 `.git`） |
| `fix` | 体检 + 修复已注册模块的异常 | ✅ 视所选策略而定 |
